# История: постмортемы и отменённые дизайны

Этот файл — не часть основной документации, которую нужно держать в голове
каждую сессию. `CLAUDE.md` подгружается ассистентом автоматически и целиком
на КАЖДЫЙ старт сессии (это его основная цена в токенах), а этот файл —
только когда кто-то явно попросил разобраться в конкретном постмортеме или
отменённой задумке. Поэтому сюда вынесено то, что полностью ЗАКРЫТО
(инцидент починен и не повторяется, фича продумана и сознательно отменена) и
не является действующим правилом/спецификацией — в отличие от «Бизнес-правил»
в CLAUDE.md, которые описывают, как код работает СЕЙЧАС, и трогать их вынос
отсюда не должен (см. заметку в самом CLAUDE.md про этот файл).

Текст перенесён дословно, без сокращений — если что-то понадобится, оно здесь
целиком, не только ссылкой.

## Реализация этапа 1 дорожной карты (v2.132.0, счётчик использования)

`UsageEvent` (models.py) без FK на `Player` (незарегистрированный тоже может нажать кнопку). `UsageMiddleware` (middleware.py) регистрируется ДВАЖДЫ в main.py — `dp.callback_query.middleware(UsageMiddleware("callback"))` и `dp.message.middleware(UsageMiddleware("command"))` — с разным `kind`, вместо одной проверки `isinstance(event, CallbackQuery/Message)` внутри: так тесты мокают событие обычным `SimpleNamespace`, не настоящими классами aiogram. Пишет в свою сессию (`async_session()` напрямую), не в `data["session"]` хендлера — сбой записи (обёрнут в `try/except Exception: logger.warning`) не роняет хендлер, откат хендлера не теряет событие. `normalize_action()`/`ACTION_LABELS`/`action_label()` — в новом `bot/services/usage.py`: числовые id вырезаются регэкспом (`player_profile_42` → `player_profile`), человеческое название экрана в `/usage` — по словарю с fallback на техническое имя для ещё не описанного экрана (не теряется молча). Пул фраз/эмодзи не нужен — таблица «действие → название» составлена по прямой просьбе пользователя вместо примера с сырыми callback_data.

## «Прогноз» — отменённая фича (дизайн от 2026-09-07/08, статус пересмотрен 2026-09-08)

Еженедельная игра-прогноз итоговых мест — параллельный мини-лидерборд поверх ELO, не путать с уже отклонённым «прогноз-голосованием на отдельный матч» (у того не было временного окна — там результат вносят сразу после игры вживую; здесь окно естественное — целая неделя). **Не в работе:** после обсуждения с командой пользователь решил отменить реализацию — «народу мало», при 5-7 игроках еженедельный прогноз-флоу не ощущается как стоящий отдельного экрана в главном меню. Дизайн ниже сохранён целиком на случай, если группа вырастет и идея снова станет актуальной — реализация НЕ запланирована.

- **Флоу:** сразу после понедельничного дайджеста (9:00 МСК) — сообщение «🔮 Прогноз на неделю» с кнопкой «Участвовать». Тап запускает пошаговый FSM (тот же паттерн, что уже есть для ввода счёта матча — накопление списка через последовательные вопросы): «Кто будет #1?» → кнопки с оставшимися игроками → выбрал → «Кто #2?» из оставшихся → ... → последнее место ставится автоматически (единственный оставшийся) → финальный экран с полным прогнозом → «Подтвердить»/«Начать заново».
- **Дедлайн** — до конца понедельника (23:59 МСК, та же граница `msk_day_start()`-стиля, что везде в проекте). Прогноз можно менять сколько угодно раз до дедлайна — повторный тап «Участвовать» перезапускает расстановку и перезаписывает предыдущий.
- **Кто в списке для расстановки:** все игроки с ≥1 матчем ЗА КАРЬЕРУ (та же граница, что уже скрывает пустые регистрации из лидерборда) — предсказывающий расставляет в т.ч. и себя самого. Игроков с 0 матчей за карьеру в список НЕ включать — им физически негде появиться в итоговом стендинге, сравнивать прогноз не с чем.
- **«Итоговое место»** = порядок в обычном стендинге лидерборда (с пиннингом чемпиона при активном боссфайте) на момент следующего понедельника — то же самое, что уже показывает «Топ недели» в дайджесте, отдельно ничего не считаем.
- **Правило очков** (готовая схема — «расстояние Спирмена», как во многих фэнтези-лигах): `очки_за_игрока = max(0, N − |прогноз_место − факт_место|)`, где N — число участников стендинга. Сумма по всем угаданным игрокам = результат недели.
- **Итоги** — в следующий понедельничный дайджест добавляется блок «🔮 Итоги прогнозов»: кто как угадал + очки за неделю.
- **Место в UI** — отдельная кнопка «🔮 Прогноз» в ГЛАВНОМ МЕНЮ (`main_menu_kb()`), не под «Статистикой»/«Рейтингом» — еженедельное участие требует лёгкой находимости каждый понедельник, а не вложенности на 2 уровня. Внутри — и текущая расстановка/участие, и накопительная таблица очков по неделям (тот же паттерн вложенных подэкранов, что уже есть у «Статистики»). НЕ добавлять на постоянную клавиатуру снизу — та зарезервирована под 3 самых частых действия (Вызвать/Рейтинг/Статистика).
- **Игрок, не голосовавший ни разу** — просто не появляется в накопительной таблице прогнозов (не 0 очков, а отсутствие строки).
- **Данные:** одна новая таблица `WeeklyPrediction(predictor_id, week_start, rankings_json)` — по одной строке на прогноз, JSON-список id по местам (тот же паттерн хранения, что уже используется для `Match.sets_data`). Очки НЕ кэшируются отдельной таблицей — считаются на лету из прогноза + фактического стендинга на момент нужного понедельника, тот же принцип, что у личных рекордов (пересчёт из истории, не кэш).

## Устранено (v2.128.1, 2026-09-17) — деплой не ставил зависимости

Деплой-скрипт (`deploy`-job в `.github/workflows/tests.yml`) никогда не устанавливал пакеты на VPS — только `git pull --ff-only` + `systemctl restart bottennis`, без единого `pip install`. Значит, любой бамп версии в `requirements.txt` тихо ложился в рабочую копию репозитория на сервере, но реально установленный пакет в венве оставался старым, пока кто-то не заходил по SSH и не прогонял `pip install` вручную. Обнаружено при ревью PR с бампом `python-dotenv` (Dependabot-алерт) — сам бамп был безопасен (уязвимая функция `set_key` в проекте не используется), но нагляднее показал, что МЕХАНИЗМ доставки пакетов на прод отсутствовал в принципе; `requirements.txt` до этого менялся всего дважды за всю историю проекта (при первом коммите и при добавлении `greenlet`), поэтому пробел ни разу не всплывал на практике. **Фикс:** добавлен шаг `/opt/bottennis/.venv/bin/pip install -r requirements.txt` между `git pull` и `systemctl restart`, с той же защитой `set -e` + явной проверкой кода возврата, что и у `git pull` (см. фикс от 2026-09-02 ниже) — если `pip install` упадёт (например, PyPI недоступен с VPS), деплой останавливается ДО рестарта сервиса, прод остаётся на предыдущей рабочей версии с прежними пакетами, а не тихо перезапускается с устаревшими зависимостями под зелёной галочкой. Только `requirements.txt` — `requirements-dev.txt` (pytest/ruff/mypy) на проде не нужен и не устанавливается.

## Устранено (2026-09-02) — деплой был зелёным, а прод не обновлялся

Релиз v2.107.0 вживую показал, что `deploy`-job могла быть зелёной, а прод при этом оставался на старой версии. Причина — VPS клонировал репозиторий по анонимному HTTPS (`https://github.com/...`), а GitHub на аутентифицированном шаге `git-upload-pack` (сама передача пакета объектов, не первичный ref listing — тот проходил на 200 без проблем) стал отвечать `401 Unauthorized` именно с IP этого VPS (похоже на антиабьюз-эвристику по дата-центровым адресам — с обычной домашней/рабочей сети то же самое клонирование проходит штатно). При этом `git pull --ff-only` в скрипте деплоя ничем не был защищён — при его падении bash-скрипт (`appleboy/ssh-action`) просто ехал на следующую строку, `systemctl restart bottennis` рестартовал сервис со СТАРЫМ кодом (working tree не менялся), встроенная проверка «сервис активен после рестарта» это не ловила (сервис-то активен, просто не то запустил), и джоба репортила успех.

**Фикс — два независимых слоя:** (1) `origin` на VPS переключён с анонимного HTTPS на SSH через отдельный read-only deploy key (`~/.ssh/bottennis_deploy_key`, добавлен в GitHub repo → Settings → Deploy keys без права записи) — тот же git-протокол, что более надёжно проходит с дата-центровых IP, не завязан на анти-абьюз эвристику анонимного HTTPS; (2) в `.github/workflows/tests.yml` деплой-скрипт получил `set -e` и явную проверку кода возврата `git pull --ff-only` с `echo "::error::..."` — теперь при повторении подобной проблемы (любой) джоба падает явно и прод остаётся на предыдущей рабочей версии, а не тихо доезжает до рестарта со старым кодом под зелёной галочкой. Экстренный ручной синк на момент инцидента (пока deploy key ещё не был добавлен) сделан через `git bundle` (полный набор объектов создан локально, перенесён на VPS через `pscp`, применён `git fetch <bundle> main:<tmp-ref>` + `git merge --ff-only`) — обходит сеть до GitHub полностью, безопасный способ синхронизировать git-историю без доверенного канала до origin.
