## Реализация этапа 1 дорожной карты (v2.132.0, счётчик использования)

`UsageEvent` (models.py) без FK на `Player` (незарегистрированный тоже может нажать кнопку). `UsageMiddleware` (middleware.py) регистрируется ДВАЖДЫ в main.py — `dp.callback_query.middleware(UsageMiddleware("callback"))` и `dp.message.middleware(UsageMiddleware("command"))` — с разным `kind`, вместо одной проверки `isinstance(event, CallbackQuery/Message)` внутри: так тесты мокают событие обычным `SimpleNamespace`, не настоящими классами aiogram. Пишет в свою сессию (`async_session()` напрямую), не в `data["session"]` хендлера — сбой записи (обёрнут в `try/except Exception: logger.warning`) не роняет хендлер, откат хендлера не теряет событие. `normalize_action()`/`ACTION_LABELS`/`action_label()` — в новом `bot/services/usage.py`: числовые id вырезаются регэкспом (`player_profile_42` → `player_profile`), человеческое название экрана в `/usage` — по словарю с fallback на техническое имя для ещё не описанного экрана (не теряется молча). Пул фраз/эмодзи не нужен — таблица «действие → название» составлена по прямой просьбе пользователя вместо примера с сырыми callback_data.

## «Прогноз» — отменённая фича (дизайн от 2026-09-07/08, статус пересмотрен 2026-09-08)

Еженедельная игра-прогноз итоговых мест — параллельный мини-лидерборд поверх ELO, не путать с уже отклонённым «прогноз-голосованием на отдельный матч» (у того не было временного окна — там результат вносят сразу после игры вживую; здесь окно естественное — целая неделя). **Не в работе:** после обсуждения с командой пользователь решил отменить реализацию — «народу мало», при 5-7 игроках еженедельный прогноз-флоу не ощущается как стоящий отдельного экрана в главном меню. Дизайн ниже сохранён целиком на случай, если группа вырастет и идея снова станет актуальной — реализация НЕ запланирована.

- **Флоу:** сразу после понедельничного дайджеста (9:00 МСК) — сообщение «🔮 Прогноз на неделю» с кнопкой «Участвовать». Тап запускает пошаговый FSM (тот же паттерн, что уже есть для ввода счёта матча — накопление списка через последовательные вопросы): «Кто будет #1?» → кнопки с оставшимися игроками → выбрал → «Кто #2?» из оставшихся → ... → последнее место ставится автоматически (единственный оставшийся) → финальный экран с полным прогнозом → «Подтвердить»/«Начать заново».
- **Дедлайн** — до конца понедельника (23:59 МСК, та же граница `msk_day_start()`-стиля, что везде в проекте). Прогноз можно менять сколько угодно раз до дедлайна — повторный тап «Участвовать» перезапускает расстановку и перезаписывает предыдущий.
- **Кто в списке для расстановки:** все игроки с ≥1 матчем ЗА КАРЬЕРУ (та же граница, что уже скрывает пустые регистрации из лидерборда) — предсказывающий расставляет в т.ч. и себя самого. Игроков с 0 матчей за карьеру в список НЕ включать — им физически негде появиться в итоговом стендинге, сравнивать прогноз не с чем.
- **«Итоговое место»** = порядок в обычном стендинге лидерборда (с пиннингом чемпиона при активном боссфайте) на момент следующего понедельника — то же самое, что уже показывает «Топ недели» в дайджесте, отдельно ничего не считаем.
- **Правило очков** (готовая схема — «расстояние Спирмена», как во многих фэнтези-лигах): `очки_за_игрока = max(0, N − |прогноз_место − факт_место|)`, где N — число участников стендинга. Сумма по всем угаданным игрокам = результат недели.
- **Итоги** — в следующий понедельничный дайджест добавляется блок «🔮 Итоги прогнозов»: кто как угадал + очки за неделю.
- **Место в UI** — отдельная кнопка «🔮 Прогноз» в ГЛАВНОМ МЕНЮ (`main_menu_kb()`), не под «Статистикой»/«Рейтингом» — еженедельное участие требует лёгкой находимости каждый понедельник, а не вложенности на 2 уровня. Внутри — и текущая расстановка/участие, и накопительная таблица очков по неделям (тот же паттерн вложенных подэкранов, что уже есть у «Статистики»). НЕ добавлять на постоянную клавиатуру снизу — та зарезервирована под 3 самых частых действия (Вызвать/Рейтинг/Статистика).
- **Игрок, не голосовавший ни разу** — просто не появляется в накопительной таблице прогнозов (не 0 очков, а отсутствие строки).
- **Данные:** одна новая таблица `WeeklyPrediction(predictor_id, week_start, rankings_json)` — по одной строке на прогноз, JSON-список id по местам (тот же паттерн хранения, что уже используется для `Match.sets_data`). Очки НЕ кэшируются отдельной таблицей — считаются на лету из прогноза + фактического стендинга на момент нужного понедельника, тот же принцип, что у личных рекордов (пересчёт из истории, не кэш).

## Устранено (v2.128.1, 2026-09-17) — деплой не ставил зависимости

Деплой-скрипт (`deploy`-job в `.github/workflows/tests.yml`) никогда не устанавливал пакеты на VPS — только `git pull --ff-only` + `systemctl restart bottennis`, без единого `pip install`. Значит, любой бамп версии в `requirements.txt` тихо ложился в рабочую копию репозитория на сервере, но реально установленный пакет в венве оставался старым, пока кто-то не заходил по SSH и не прогонял `pip install` вручную. Обнаружено при ревью PR с бампом `python-dotenv` (Dependabot-алерт) — сам бамп был безопасен (уязвимая функция `set_key` в проекте не используется), но нагляднее показал, что МЕХАНИЗМ доставки пакетов на прод отсутствовал в принципе; `requirements.txt` до этого менялся всего дважды за всю историю проекта (при первом коммите и при добавлении `greenlet`), поэтому пробел ни разу не всплывал на практике. **Фикс:** добавлен шаг `/opt/bottennis/.venv/bin/pip install -r requirements.txt` между `git pull` и `systemctl restart`, с той же защитой `set -e` + явной проверкой кода возврата, что и у `git pull` (см. фикс от 2026-09-02 ниже) — если `pip install` упадёт (например, PyPI недоступен с VPS), деплой останавливается ДО рестарта сервиса, прод остаётся на предыдущей рабочей версии с прежними пакетами, а не тихо перезапускается с устаревшими зависимостями под зелёной галочкой. Только `requirements.txt` — `requirements-dev.txt` (pytest/ruff/mypy) на проде не нужен и не устанавливается.

## Устранено (2026-09-02) — деплой был зелёным, а прод не обновлялся

Релиз v2.107.0 вживую показал, что `deploy`-job могла быть зелёной, а прод при этом оставался на старой версии. Причина — VPS клонировал репозиторий по анонимному HTTPS (`https://github.com/...`), а GitHub на аутентифицированном шаге `git-upload-pack` (сама передача пакета объектов, не первичный ref listing — тот проходил на 200 без проблем) стал отвечать `401 Unauthorized` именно с IP этого VPS (похоже на антиабьюз-эвристику по дата-центровым адресам — с обычной домашней/рабочей сети то же самое клонирование проходит штатно). При этом `git pull --ff-only` в скрипте деплоя ничем не был защищён — при его падении bash-скрипт (`appleboy/ssh-action`) просто ехал на следующую строку, `systemctl restart bottennis` рестартовал сервис со СТАРЫМ кодом (working tree не менялся), встроенная проверка «сервис активен после рестарта» это не ловила (сервис-то активен, просто не то запустил), и джоба репортила успех.

**Фикс — два независимых слоя:** (1) `origin` на VPS переключён с анонимного HTTPS на SSH через отдельный read-only deploy key (`~/.ssh/bottennis_deploy_key`, добавлен в GitHub repo → Settings → Deploy keys без права записи) — тот же git-протокол, что более надёжно проходит с дата-центровых IP, не завязан на анти-абьюз эвристику анонимного HTTPS; (2) в `.github/workflows/tests.yml` деплой-скрипт получил `set -e` и явную проверку кода возврата `git pull --ff-only` с `echo "::error::..."` — теперь при повторении подобной проблемы (любой) джоба падает явно и прод остаётся на предыдущей рабочей версии, а не тихо доезжает до рестарта со старым кодом под зелёной галочкой. Экстренный ручной синк на момент инцидента (пока deploy key ещё не был добавлен) сделан через `git bundle` (полный набор объектов создан локально, перенесён на VPS через `pscp`, применён `git fetch <bundle> main:<tmp-ref>` + `git merge --ff-only`) — обходит сеть до GitHub полностью, безопасный способ синхронизировать git-историю без доверенного канала до origin.

- **У игрока может быть только ОДИН активный матч одновременно** (стол один, матчи строго последовательные) — единый источник правды `get_active_match(session, player_id)` в `utils.py`, используется в 5 местах: `show_players_for_challenge`/`send_challenge` (challenge.py — заранее прячет из списка вызова всех занятых игроков и авторитетно блокирует на момент вызова, страхует от гонок и от кнопки «Реванш», которая идёт в обход списка), `show_player_profile`/`h2h_kb`-звонок в `show_h2h` (прячут кнопку «⚔️ Вызвать», если занят зритель ИЛИ владелец профиля/соперник по H2H — раньше проверялась только пара «есть ли активный матч именно между этими двумя», из-за чего кнопка вела в тупик), `show_my_matches` (history.py — если занят зритель, кнопки «Вызвать X» в блоке «С кем сыграть?» не показываются вообще, хотя инфо-строки по соперникам остаются). Старый точечный кейс «уже есть активный матч именно с этим соперником» — частный случай общего правила, отдельно не проверяется.

- **Босс-файт за 1-е место** (с v2.84.0, харденинг в v2.85.0). Чемпион — `Player.is_champion` (единственный `True` в клубе), не пересчитывается на лету. Если чемпион не назначен ни у кого — фича полностью неактивна: сортировка чисто по рейтингу, без кнопок/эмодзи/уведомлений (`bootstrap_champion` в `init_db()` фиксирует текущего лидера при первом старте после апдейта, без порога матчей — это фиксация положения, не передача власти; тот же флаг служит ручным рубильником — `UPDATE players SET is_champion=0`). Факт «фича когда-либо активировалась» хранится отдельно, в `ChampionReign` (ниже) — иначе `bootstrap_champion` переизбирал бы чемпиона заново на каждом деплое/рестарте, игнорируя ручное отключение. **Претендент** — `get_challenger()`, вычисляется на лету (не хранится): не чемпион, рейтинг строго выше чемпионского, ≥`NEWCOMER_THRESHOLD` (15) завершённых матчей; если порог не набран — претендента НЕТ ВООБЩЕ, право не откатывается на следующего по рейтингу. Пара (чемпион, текущий претендент) автоматически становится боссфайтом при создании матча (`Match.is_boss_fight`) независимо от способа вызова. Ничья запрещена — проверка в `finish_sets()`, страховка в `confirm_result()` (не только в трёх местах ввода счёта — все сходятся к одной из этих двух точек). Дельта ×2 (`BOSS_FIGHT_MULT`), `repeat_multiplier` не применяется. Победил претендент → трон переходит; победил чемпион → не меняется (обе ветки — в `confirm_result()`, match_result.py). Реванш между парой заблокирован (`boss_fight_rematch_blocked()`), пока НЕЧЕМПИОН пары (текущий, не исторический — переопределяется живьём через `get_champion()`) не завершит матч с третьим игроком; матчи текущего чемпиона пары блок не снимают; отменённый (`declined`) боссфайт блок не включает — проверяется и в `send_challenge` (авторитетно), и в видимости кнопок (`can_challenge` в profile.py/history.py, список/ярлык в challenge.py — та же логика, что уже применена к `get_active_match`, иначе кнопка ведёт в тупик). Авто-освобождение трона — та же часовая джоба, что и напоминания о матчах (`check_champion_auto_release`, scheduler.py): чемпион не завершал матчей >14 дней (`CHAMPION_INACTIVITY_DAYS`, было 7 до v2.135.3 — живая жалоба пользователя: неделя оказалась слишком коротким сроком терпимости для клуба, где перерывы в игре — обычное дело) → трон топу по очкам среди игроков с ≥15 матчей, без боя; кандидатов нет — трон остаётся; **пропускает цикл, если у чемпиона сейчас есть активный матч** (в т.ч. собственный боссфайт) — иначе трон мог гонкой достаться постороннему прямо во время чужого поединка за него. Смена `Player.is_champion` — **только через `try_transfer_champion()`** (CAS: `UPDATE ... WHERE is_champion=True AND id=<from>`, тот же паттерн, что у `Match.status`) в обоих местах переноса (авто-освобождение и `confirm_result`) — если трон уже сменился где-то ещё, перенос тихо отменяется вместо порчи данных (без этого второй чемпион одновременно ронял бы `get_champion()` с `MultipleResultsFound`). Гонка в `send_challenge` (создание дублирующихся активных матчей) закрыта `asyncio.Lock`-ом в v2.135.0 (см. «Известные ограничения» ниже, раздел «Устранено») — распространяется и на боссфайт автоматически, отдельно от гонки за трон.

Самая насыщенная и намеренно многословная сводка из всех — единственное сознательное исключение из правила «не простыня, режь на группы» (см. остальные экраны проекта): это письмо раз в год, а не экран, который открывают на бегу. Полный табель клуба (не топ-3, а все игроки, как и в квартальной), чемпион года (текущий чемпион на момент отправки, не анализ смены трона за год), взлёт/падение года, нагибатор года, дерби года, «без поражений»/«американские горки» года, топ-матч года — плюс к каждому из этих разделов приклеена ОДНА конкретная зафиксированная фраза-отсылка (не пул со случайным выбором, как у пасхалок — согласовано с пользователем построчно). Сознательно не считает, сколько ачивок/личных рекордов разблокировано за год — ни ачивки, ни личные рекорды не хранят дату получения, посчитать за период невозможно без новой инфраструктуры (не выйти было бы за рамки уже одобренного скоупа).

- **Репортаж матча** (`match_report()`, utils.py, v2.101.0) — расширяет короткую `match_drama_reason()` в связный абзац для топ-матча периода (используется в «Топ-матч дня»/«Матч недели»/«Матч месяца»/«Топ-матч квартала»/«Топ-матч года» — все 5 периодических дайджестов, и в карточке «поделиться победой»; «Самый эпичный матч» в рекордах клуба сознательно НЕ тронут, там плотный список, длинный абзац туда не подходит). Собирается из фраз-кусочков по 4 факторам (камбэк — проигрывал именно ПЕРВЫЕ ДВЕ партии, строже, чем «камбэк» в `match_drama_reason`, которому хватает одной; марафон 5+ партий; дьюс именно на РЕШАЮЩЕЙ партии, не любой; апсет ≥20 pts), фиксированные фразы, не LLM-генерация на лету. Если ни один из 4 факторов не сработал — пробует `match_drama_reason()`; если и та упала на одну из двух плоских строк («Уверенный разгром»/«Напряжённый матч») — с v2.105.0 подставляется фраза из `BLOWOUT_PHRASES`/`PLAIN_WIN_PHRASES` (по 7 штук, индекс по `match.id`, тот же принцип стабильности, что у `match_phrase`) — на живом скрине пользователь заметил, что плоская строка на карточке победы выглядит скучно. Более содержательные исходы `match_drama_reason()` (дьюс на тоненького, решилось в последней партии) не подменяются — под них фраз-пула нет и не нужно. **Пулы 4 факторных фрагментов (`COMEBACK_OPENERS`/`MARATHON_FRAGMENTS`/`DEUCE_FRAGMENTS`/`UPSET_FRAGMENT_TEMPLATES`) индексируются через `_stable_pool_index(seed, salt, pool_len)`** (v2.119.0, utils.py) — MD5-хэш от `f"{seed}:{salt}"`, НЕ линейное смещение (`m.id`, `m.id+1`, `m.id+2`...). Причина: когда все 4 пула выросли до одинакового размера (8 фраз каждый), простое линейное смещение перестало реально декоррелировать факторы — для ЛЮБОЙ линейной функции `(x*k + c) % n` результат полностью определяется `x mod n`, поэтому комбинация индексов НЕСКОЛЬКИХ пулов одинакового размера n математически не может иметь больше n вариантов, какой множитель k ни возьми (регресс-тест на декорреляцию поймал это сразу). Первая попытка чинить через `zlib.crc32` тоже не сработала — CRC32 линеен над GF(2) и не даёт лавинного эффекта на похожих коротких строках (соседние `match.id` давали заметно коррелирующие остатки). MD5 — настоящий криптографический хэш, декоррелирует независимо от размеров пулов. **«Мягкие» факторы (v2.131.0)** — живая жалоба «опять скучные репорты в итогах дня»: у клуба типичный формат до 2 побед, где камбэк с 0:2 и марафон на 5 партий физически не бывают, поэтому топ-матчем чаще всего становился обычный матч из 3 партий (проигранная первая, дьюс в НЕ решающей партии, 2:1 впритык), а строгие 4 фактора его не ловили и репортаж откатывался на сухие строки `match_drama_reason()`. Добавлены пулы `SOFT_COMEBACK_OPENERS`/`CLOSE_DECIDER_FRAGMENTS`/`MID_DEUCE_FRAGMENTS` (тот же принцип сборки и тот же `_stable_pool_index` с отдельной солью на пул); срабатывают только если ни один строгий фактор не сработал. В `match_report` остаются на сухом откате только ничьи (`Ничья в равной борьбе`), сознательно не трогали. Урок на будущее: при следующем расширении любого из пулов фраз в проекте — если после этого несколько пулов окажутся одного размера, декорреляция может незаметно деградировать, стоит перепроверить регресс-тестом на разнообразие, не полагаться на визуальный осмотр кода.

**Устранено (v2.135.0, 2026-09-28):** гонка в правиле «один активный матч одновременно» (`send_challenge`, `bot/handlers/challenge.py`, была с v2.79.0) — проверка «нет ли уже активного матча» (`get_active_match`) и создание нового `Match` были двумя отдельными шагами без атомарной защиты; два почти одновременных вызова (двойной тап, или два игрока вызывают друг друга в одну секунду) теоретически могли оба пройти проверку до коммита первого `INSERT`. Фикс — `asyncio.Lock` (`_CHALLENGE_LOCK` в challenge.py) вокруг всего блока «проверка занятости → детект боссфайта → проверка занятости соперника → создание матча»: бот работает одним Python-процессом (long polling), гонка возникала только из-за того, что aiogram обрабатывает апдейты параллельными asyncio-тасками ВНУТРИ этого процесса — обычного `asyncio.Lock` достаточно, атомарная перепроверка на уровне БД (CAS/SERIALIZABLE) не нужна и не сделана: она стоила бы дороже ради того же результата на масштабе 5-7 игроков за одним столом. Фикс проверен регресс-тестом, который **действительно ловит гонку**: `test_send_challenge_race_closed_by_lock` через `db_factory` (общая `:memory:` БД, независимые сессии) запускает 2 конкурентных `send_challenge()` на одного соперника через `asyncio.gather` — при временно отключённом `_CHALLENGE_LOCK` тест падал 5/5 запусков (создавались 2 активных матча), с локом — 806/806 тестов зелёные. Босс-файт (v2.84.0), создающийся через ту же `send_challenge`, унаследовал фикс автоматически — отдельно ничего чинить не пришлось.
