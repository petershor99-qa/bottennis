# Этап 1: пассивный счётчик использования экранов

Сначала выполни «Общий порядок работы над любым этапом» из CLAUDE.md (раздел «🗺 Дорожная карта»), шаги 1–3. Если этап 1 уже ✅ — остановись.

## Зачем

Пользователь хочет понять, какими экранами бота реально пользуются, чтобы позже (этап 4) убрать неиспользуемое. Опрашивать игроков бесполезно — никто не отвечает. Поэтому бот должен **молча** записывать, какие экраны открывают. Игроки ничего не замечают: никаких новых сообщений, кнопок, текстов для них.

## Что сделать

**1. Модель** — новый класс в `bot/db/models.py`, таблица `usage_events`:
- `id` — PK
- `user_id` — Telegram user id (int, **без** FK на players: незарегистрированный тоже может нажать кнопку)
- `action` — строка до 64 символов, нормализованное имя экрана (см. п. 2)
- `created_at` — naive UTC, как везде в проекте: `default=lambda: datetime.now(timezone.utc).replace(tzinfo=None)`

Новая таблица создастся сама через `Base.metadata.create_all` в `init_db()` (`bot/db/database.py`) — ALTER-миграция не нужна. Индекс на `created_at` — да.

**2. Нормализация** — чистая функция `normalize_action(raw: str) -> str` (положи в `bot/utils.py` или новый `bot/services/usage.py`): убирает числовые сегменты, чтобы `player_profile_42` и `player_profile_7` считались одним экраном. Правило: удалить все сегменты вида `_<число>` (включая отрицательные) — `player_profile_42` → `player_profile`, `h2h_5_0` → `h2h`, `cancel_match_42` → `cancel_match`, `menu_stats` → `menu_stats`. Для команд — имя команды без аргументов: `/start ABC123` → `/start`. Обрезать до 64 символов.

**3. Middleware** — `UsageMiddleware` в `bot/middleware.py`:
- Регистрируется в `main.py` на `dp.callback_query` (все нажатия кнопок) и на `dp.message` — но на сообщения пишет событие **только для команд** (текст начинается с `/`). Прямой ввод счёта (`11:7 9:11`) и прочий текст — не записывать.
- Пишет событие в **своей отдельной** короткой сессии (`async_session()` из `bot/db/database.py`), не в `data["session"]` хендлера: откат транзакции хендлера не должен терять событие, а ошибка записи события — ронять хендлер.
- Запись — **после** вызова хендлера, в `finally`, обёрнутая в `try/except Exception` с `logging.warning(...)`: счётчик никогда не должен ломать бота или показывать пользователю ошибку.
- `user_id` — `event.from_user.id`; если `from_user` нет — событие пропустить.

**4. Команда `/usage`** — в `bot/handlers/admin.py`, по образцу `/dbstats`: только для админа (`_is_admin`, для остальных молча игнорировать), длинный вывод — через уже существующий `_send` (режет по 4000 символов). Период — последние 30 дней. Для каждого `action`: число открытий, число разных пользователей, последнее открытие (дата по МСК, `MSK_OFFSET`). Сортировка по числу открытий, по убыванию. В шапке: период и общее число событий. Если данных нет — короткое сообщение об этом. Добавь `/usage` в докстринг модуля admin.py (список команд).

Точные тексты сообщения `/usage` — служебные, для админа, но всё равно покажи пользователю пример вывода перед реализацией (правило из «Общего порядка», шаг 4).

**Админские нажатия тоже считаются** (админ — такой же игрок). Отдельно отфильтровывать не надо: колонка «разных пользователей» покажет, если экран открывал только один человек.

## Тесты

- `normalize_action` — параметризованный тест на все примеры из п. 2 плюс строку без чисел и длинную строку (> 64).
- Middleware пишет событие на callback и на команду, **не** пишет на обычный текст; ошибка записи события не роняет хендлер (подмени сессию так, чтобы запись падала, — хендлер всё равно отработал). Для подмены `async_session` — тот же приём, что у тестов планировщика: фикстура `db_factory` + `monkeypatch.setattr(<модуль>, "async_session", db_factory)` (подменять в модуле, который её **использует**, а не в `bot.db.database`).
- `/usage`: не-админ — тишина; админ — агрегаты верные (открытия, разные пользователи), события старше 30 дней не попадают; пустая таблица — сообщение «нет данных».

## Приватность

Репозиторий публичный — в коде, тестах и доках никаких реальных имён и id. Данные лежат только в БД на VPS.

## Готово, когда

Тесты и ruff зелёные, релиз выпущен скиллом `release`, **деплой подтверждён**, и в таблице дорожной карты у этапа 1 стоит «✅ vX.Y.Z, выкачен YYYY-MM-DD» — от этой даты этап 4 отсчитывает свои 28 дней, поэтому дата должна быть датой фактической выкатки в прод. В CLAUDE.md опиши счётчик рядом с другими админ-командами. Скажи пользователю: данные копятся с сегодняшнего дня, `/usage` в Telegram можно смотреть в любой момент, этап 4 — не раньше чем через 4 недели.
